## Context

- Current git status: `git status`
- Current branch: `git branch --show-current`
- Files changed vs main: `git diff main...HEAD --name-only`
- Code changes summary: `git diff main...HEAD --stat`
- Detailed code changes: `git diff --no-pager main...HEAD`
- Recent commits on this branch: `git log --oneline --no-merges main..HEAD`
- Commit messages for context: `git log --pretty=format:"%h %s" main..HEAD`
- Remote status: `git status -b --porcelain`

## Your task

Create a GitHub pull request for the current branch following these steps:

### Step 1: Analyze Changes
1. Review the git diff and commit history to understand what changes are being made
2. Analyze the code changes for a comprehensive summary
3. Identify the type of changes (feat, fix, refactor, docs, etc.)
4. Determine the scope and impact of the changes

### Step 2: Check for PR Template
1. Look for GitHub PR templates in common locations:
   - `.github/pull_request_template.md`
   - `.github/PULL_REQUEST_TEMPLATE.md`
   - `.github/PULL_REQUEST_TEMPLATE/`
2. If found, read and use as the base structure for the PR description

### Step 3: Prepare PR Details
To calculate the title the default approach is to use the reference from the implement tasks and the naming guidelines in PR Template.
- Examples for implemented  T123 - REF-001 and T345 - REF-002: feat: LEV-123, LEV:-456
If the title too long use conventional commits format: `type(scope): description`
- Examples: `feat(api): add user authentication`, `fix(ui): resolve mobile layout issues`
1. **Title**: <calculated title>
2. **Description**: Include:
   - Brief summary of changes
   - Motivation/context for the changes
   - Any breaking changes
   - Testing information
   - Checklist items (if from template)

### Step 4: Ask for Clarifications
Before creating the PR, ask the user:
1. Should this be a draft PR? (--draft flag)
2. Confirm the PR title and description

### Step 5: Create PR
1. Ensure the current branch is pushed to remote
2. Use `gh pr create` with the prepared title and description
3. Add draft flag if requested
4. Provide the PR URL for review

## Guidelines

- Follow conventional commits for PR titles: https://www.conventionalcommits.org/en/v1.0.0/
- Use clear, descriptive language
- Include context for why changes were made
- Reference any related issues with `Closes #123` or `Fixes #456`
- Present the final PR title and description for user approval before submission
- Keep PR descriptions concise and to the point, only adding key information. You don't have to describe every single feature or implementation detail from the code, only the key ones.
- DO NOT ADD A REFERENCE TO THIS BEING GENERATED BY CLAUDE
- Do not add any extra superlatives, be concise and to the point - you're there to help engineers understand the changes with few words, not to show off the changes.
- Don't add unnecessary fluff (e.g. instead of `Lightning fast UI for management` just say `UI for management`.)
